# npm release

The intended package is `@nikhilvijayakumar/prati`. Confirm ownership of the npm scope and package availability before publishing. The first release requires an authenticated npm account with permission to publish to that scope; the guide's initial manual publish is needed before configuring a trusted publisher on an existing package. Build and validate before publishing; published versions cannot be overwritten.

After the first publication, configure an npm trusted publisher for GitHub owner `NikhilVijayakumar`, repository `Prati`, workflow `publish.yml`, and environment `npm`. Leave direct `npm publish` and `npm dist-tag` permissions disabled; staged publishing is allowed by default. Create and protect the matching GitHub environment according to repository policy. New trusted publisher configurations expire if their first successful publish does not occur within two days. See [npm trusted publishing](https://docs.npmjs.com/trusted-publishers/).

Merge the reviewed version and matching lockfile, create and push a matching `v<version>` tag according to repository policy. The workflow validates, tests, builds and stages the package using OIDC. A successful workflow means the package was staged, not published. Review the staged package in the npm Staged Packages tab (or use `npm stage list`, `npm stage view <stage-id>`, and `npm stage download <stage-id>`). Approve it on npm or with `npm stage approve <stage-id>` using 2FA. Verify the published registry version and install it in a clean consumer after approval. Staged publishing requires npm CLI 11.15.0 or newer. Do not assume a tag or workflow succeeds without checking its result.

Existing imports can change to `@nikhilvijayakumar/prati`, or an npm alias can retain `prati`: `npm install prati@npm:@nikhilvijayakumar/prati`. Commit the consumer lockfile.
